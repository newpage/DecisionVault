# Engineering handbook

## Delivery path

The supported flow is:

```text
Mac workstation → GitHub → Linux server → Apache HTTPS → users
```

Source changes are developed, built, tested, reviewed, and committed on the Mac workstation. GitHub is the handoff and CI point. Runtime deployment and diagnosis occur on the Linux server. In particular, `dv deploy` and `dv doctor` are Linux server commands, not Mac development commands.

## Mac workstation: build and test

Create a local environment without committing it:

```bash
cp .env.example .env
# Replace JWT_SECRET and review local URLs before starting.
# Set CORS_ORIGINS=http://localhost:3200
# Set NEXT_PUBLIC_API_URL=http://localhost:8200/api/v1
docker compose up --build
```

The Compose defaults publish the backend at `http://127.0.0.1:8200` and frontend at `http://127.0.0.1:3200`. The two URL settings above align the browser client and backend CORS policy with those host-port defaults; the current `.env.example` still contains older URL values. `DV_BACKEND_PORT` and `DV_FRONTEND_PORT` can override the published host ports, in which case the URL settings must change with them. A destructive clean start is available as `./scripts/reset-and-start.sh`; it removes local database and storage volumes, so use it only when losing local data is acceptable.

Run the same core checks as CI:

```bash
cd apps/backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
ruff check app tests
pytest

cd ../frontend
npm install
npm run build

cd ../..
docker compose build
```

The top-level `tests/test_knowledge_module.py` is not invoked by the current CI workflow; run `python -m pytest tests` from the repository root when changing the covered knowledge module behavior.

## Mac workstation: commit and publish for review

```bash
git status --short
git diff --check
git diff
git add <reviewed-files>
git commit -m "Describe the focused change"
git push
```

Do not commit or push until the requested review/approval has occurred. Confirm CI passes on GitHub before server deployment.

## Linux server: prepare and diagnose

From the checked-out repository, create `.env`, retain a strong `JWT_SECRET`, set the public CORS origin and `/api/v1` browser API path, and install the repository CLI if desired:

```bash
chmod +x scripts/*.sh scripts/dv
sudo ./scripts/install-dv-cli.sh
dv doctor
```

`dv doctor` checks the server checkout, Docker/Compose, configuration, resolved published ports, local backend/frontend health, public HTTPS, optional Ollama health, backup-directory writability, and disk space. Run it on the Linux server.

## Linux server: backup and deploy

For a normal release:

```bash
cd /path/to/DecisionVault
dv doctor
dv backup
dv deploy --test
dv status
```

`dv deploy` refuses a dirty tree, fetches and fast-forwards the configured branch (default `main`), optionally runs backend tests, rebuilds/starts the combined Compose stack, waits for localhost health, and checks the public URL. Use `dv deploy --reset-db` only for an explicitly approved breaking release: it permanently deletes the database and storage volumes before rebuilding.

Other server commands:

```bash
dv logs all 200
dv logs backend 300
dv status
dv diag
```

`dv diag` creates a redacted diagnostic archive in the repository. Review it before sharing; redaction patterns reduce risk but are not a guarantee.

## Rollback

There is no automated rollback or restore command in this repository. For a code-only rollback that is compatible with the current data:

1. Identify the last known-good commit and verify its release notes and schema compatibility.
2. On the Mac, create and test a normal revert commit (`git revert <bad-commit>`), push it, and let CI pass.
3. On the Linux server, run `dv backup`, then `dv deploy --test` to deploy that new revert commit from the configured branch.
4. Run `dv doctor`, smoke-test through public HTTPS, and inspect logs.

Do not use `dv update` as a rollback mechanism: it resets the clean server checkout to the latest remote branch. Database/storage restore is currently a manual, unverified procedure; preserve the backup generated by `dv backup` and require an approved recovery plan before destructive database work.

## Troubleshooting

1. Run `dv doctor` and `dv status` on the Linux server.
2. Inspect the affected service with `dv logs <service> 300`.
3. Check `docker compose` resolution, disk capacity, `.env`, and whether host ports match `DV_BACKEND_PORT`/`DV_FRONTEND_PORT`.
4. For public-only failures, verify Apache routes `/api/` and `/health` to backend localhost and `/` to frontend localhost, with the API rule first; verify TLS and `CORS_ORIGINS`.
5. For ingestion failures, inspect worker logs, shared storage, database health, supported file type, and Ollama reachability. Missing Ollama embeddings should degrade safely, but model-dependent quality will differ.
6. Create `dv diag` only when a diagnostic bundle is useful, then inspect it for sensitive information before transfer.

## Security and review gates

Every change touching tenant data must include a cross-tenant test or a documented reason it cannot. Review authentication, authorization, classification, access policy, caches, retrieval/ranking order, background jobs, storage paths, logs, and error messages. Never relax localhost-only service publishing or expose PostgreSQL/worker ports as a routine debugging shortcut.
